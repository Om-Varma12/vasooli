**Why this shape, in one paragraph:** the pipeline is `ingest -> enrich -> classify -> decide
-> execute -> audit/report`, and the folder structure IS the pipeline — six stages, six
folders, each with a clear public entrypoint (`__init__.py` or the one file in it) and
private implementation details behind that entrypoint. Nothing about `classify` knows
`execute` exists. Nothing about `decide` knows what channel will carry out its decision.
That's not architecture for its own sake — it's what lets you swap the synthetic-JSON
ingest for a real webhook listener on Day 6 by writing new code in `ingest/` and touching
nothing else.

## 2. What "LIVE" vs "STUB" means, precisely

**LIVE** = real logic, runs today, covered by tests, is what `scripts/run_demo.py` actually
executes. This is `classify/`, `decide/`, `execute/` (with real API integrations for WhatsApp/Voice),
`audit/`, `report/`, `orchestrator.py`, `worker.py`, `ingest/`, and `enrichment/`.

**STUB** = the file exists, has the right function signatures, has a docstring explaining
exactly what the real implementation should do and often a code sketch of it — but the body
either raises `NotImplementedError` or returns a clearly-marked placeholder. This is
`execute/rate_limiter.py` and the LLM call inside
`classify/llm_classifier.py`.

If you're asked in the panel "does this actually work end to end" — the honest answer is:
**the decision-making core works end to end, for real, on synthetic data shaped like real
Razorpay payloads.** The parts that talk to the outside world (real webhooks, real WhatsApp,
real voice, real LLM calls) are stubbed with a clear, specific plan, not hand-waved.

## 3. How a record actually flows through the system today

Trace one record from `data/failed_payments_batch.json` through `scripts/run_demo.py`:

1. `orchestrator.load_batch()` reads the JSON, builds a `FailureEvent` per record (ingest is
   currently just this — a stand-in for what a real webhook listener would produce).
2. `orchestrator.run_one(event, audit)` calls, in order:
   - `classify.classify(event)` →
     - `cancellation_gate.is_cancellation_intent(event)` first. If true, returns
       `(CANCELLATION_INTENT, reason, 1.0, "gate")` immediately — nothing else in
       `classify/` runs.
     - else `rules_classifier.classify_by_rule(event)` — dict lookup on `reason_code`.
       Returns a match for ~92% of records.
     - else `llm_classifier.classify_by_llm(event)` — the stub. Returns `(UNKNOWN, reason,
       0.0)` today; will return a real classification + confidence once wired.
   - `decide.decide(event, root_cause)` →
     - `guard_clauses.run_guard_clauses(event, root_cause)` — checks cancellation (again,
       defense in depth) then the retry ceiling. If either fires, returns a `Decision`
       immediately, `rules_engine.py` is never consulted.
     - else `rules_engine.evaluate(event, root_cause)` — loads `config/rules_table.yaml`,
       finds the matching rule, builds a `Decision`. If the rule says
       `then_evaluate_voice_escalation: true`, also runs `evaluate_voice_escalation()`,
       which checks DND (hard stop, from `guard_clauses.check_dnd`), then risk tier and
       amount thresholds (from config), then the cost gate (`cost_gate.assumed_cost_inr`,
       also from config).
   - `execute.execute(event, decision)` → looks up the adapter for `decision.tier` in
     `_ADAPTERS`, calls `.send(event, decision)`, gets back the outcome dict.
   - Every step above writes a line to `audit.AuditLog` — `classify`, `policy`,
     `execute:<channel>`, `outcome`. Four lines minimum per record.
3. `orchestrator.run_batch()` does this for all 60 records.
4. `report.build_report(results)` aggregates: ₹ at risk, ₹ recovered, recovery rate, cost,
   funnel by tier, and an honest exceptions list (every unresolved record, not a curated
   sample).

That's the whole system. Nothing about this flow requires you to open more than the file
you're currently debugging — that's the point of the layer boundaries.

## 4. Design decisions worth being able to defend out loud

These come up if a panelist asks "why did you do it this way" — have the one-sentence
answer ready for each, they're all in this file so you don't have to reconstruct them live.

- **Why is the policy engine deterministic instead of an LLM deciding the action?**
  Because "explainable and bounded" means a compliance reviewer can read the exact rule
  that fired, not re-run a model and hope it explains itself the same way twice.

- **Why are the NPCI retry ceiling and DND check Python constants instead of config?**
  Because a YAML file is something a well-meaning ops person could edit at 11pm to hit a
  recovery target. The compliance guarantee is "structurally impossible to violate," not
  "usually respected" — that requires them to be outside the file a rules change could touch.

- **Why classify with a rule tier AND an LLM tier instead of just always calling an LLM?**
  Cost and speed at real volume (calling an LLM per event when 92% are a lookup table away
  from solved is wasteful) — but more importantly, auditability: for 92% of records, "why
  was this classified this way" has a one-line deterministic answer instead of a model
  generation you'd have to re-run to explain.

- **Why is the cancellation check duplicated (once in `classify/`, once in
  `decide/guard_clauses.py`)?** Deliberate defense in depth for the one decision that must
  never be wrong. If the classify-layer gate has a bug, the decide-layer guard still catches
  it before any money action fires.

- **Why is voice escalation not just another row in the rules table?** Because it depends on
  attributes of the event (risk tier, amount, DND) rather than root cause alone — it's a
  sub-decision with its own gate order (DND first, unconditionally; thresholds; cost gate
  last), and collapsing that into a flat table would hide the DND-must-be-first requirement.

- **Why config-drive the rules table and channel costs but not the ceiling/DND?** See
  above — the split itself IS the compliance argument. If someone suggests "for consistency,
  let's put everything in config," that consistency is not worth what it costs you.

## 7. How to run everything

```bash
# one-time setup
python -m venv venv && source venv/bin/activate
pip install -r requirements-dev.txt      # or: pip install -e . for just runtime deps

# generate data + run the demo (or: make demo)
python scripts/generate_synthetic_data.py
python scripts/run_demo.py

# run the test suite (or: make test)
pytest tests/ -v

# clean generated artifacts (or: make clean)
find . -type d -name __pycache__ -exec rm -rf {} +
rm -f data/failed_payments_batch.json data/audit_log.jsonl data/dead_letter.jsonl
```

CI (`.github/workflows/tests.yml`) runs `pytest` and then the full demo on every push — if
you push something that breaks `scripts/run_demo.py`, you'll know within a couple of
minutes, not when you try to film the video on Day 8.

## 9. Environment Configuration
The system relies on the following environment variables (stored in `.env`):

### Core Infrastructure
- `REDIS_URL`: Redis connection string (e.g., `redis://localhost:6379`). Used for queuing and deduplication.
- `DATABASE_URL`: Supabase PostgreSQL connection string.

### Razorpay Integration
- `RAZORPAY_WEBHOOK_SECRET`: Secret for signature verification.
- `RAZORPAY_API_KEY` / `RAZORPAY_KEY_SECRET`: For API access.

### LLM Layer
- `GROQ_API_KEY`: API key for Groq (used in classify fallback).

### Twilio WhatsApp
- `TWILIO_ACCOUNT_SID`: Twilio Account SID.
- `TWILIO_AUTH_TOKEN`: Twilio Auth Token.
- `TWILIO_SANDBOX_NUMBER`: The Sandbox number (e.g. `+1...`).
- `TEST_NUMBER`: Your verified phone number (e.g. `+91...`).
- `TWILIO_CONTENT_SID`: Approved template SID for WhatsApp.

### Twilio Voice
- `TWILIO_VOICE_FROM`: The Twilio number used to place outbound calls.
- `VOICE_BASE_URL`: The public URL (e.g. zrok) where the FastAPI server is hosted. Twilio fetches TwiML from `BASE_URL/voice/twiml`.
